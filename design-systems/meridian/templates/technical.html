Designing for
a second look.

A small, explicit review gate between an AI-generated draft and the people who will rely on it.

Discipline
Applied AI / Systems
Updated
28 September 2026
Reading time
7 minutes
Status
Design proposal
Abstract

Generation and publication are different responsibilities. This note sketches a workflow that preserves that boundary: retain the evidence, check the output, and send uncertain cases to a human. It is an explanatory example, not a production implementation.

01

One boundary. Four clear stages.

Keep the pipeline easy to inspect. Each stage produces a concrete artifact, and nothing becomes publishable simply because generation succeeded. The review gate is the point where a draft earns its next state.

The gate should check observable conditions, not ask the model how confident it feels. Are required fields present? Do cited sources exist in the approved collection? Has the content received the required human approval?

Boundary, not magic

A valid citation proves a source exists. It does not prove the source supports the claim.

02

Make the stop condition explicit.

Return a named state rather than a boolean. The caller needs to know whether an output is ready, missing evidence, or waiting for review. A useful interface carries both the result and the reason.

review-gate.ts
// Illustration: validate inputs before this boundary.
async function review(draft: Draft): Promise<Result> {
  const evidence = await checkSources(draft);

  if (!evidence.complete) {
    return {
      state: "needs-evidence",
      reasons: evidence.missing,
    };
  }

  // Approval must match this exact revision.
  if (!hasCurrentApproval(draft)) {
    return { state: "needs-review" };
  }

  return {
    state: "ready",
    revision: draft.revision,
  };
}
TypeScript · Explanatory pseudocode · Not a complete security boundary

  1. NOTE 01Evidence is an input.Retain source IDs and excerpts alongside the draft. Do not ask reviewers to rediscover them.
  2. NOTE 02Approval is versioned.Bind approval to an immutable revision. Editing the draft invalidates prior approval.
  3. NOTE 03Ready is not published.A separate release step enforces permissions, writes the audit record, and publishes atomically.
Failure is also a state

If a source service times out or an approval check throws, stop the release. A dependency failure must never be interpreted as evidence that a draft is safe to publish.

03

The trade-offs are deliberate.

Compare approaches by their operational consequences, not their novelty.
ApproachWhat it buysWhat it costsBest fit
Automatic releaseLowest latencyErrors reach readersLow-impact, reversible work
Sampled reviewLower review loadSome errors remain unseenStable, measured workflows
Required approvalAccountable decisionsHuman review capacityConsequential documents
This proposal

Use required approval for consequential documents. Introduce lighter review only after the team can describe the failure modes, measure their frequency, and accept their impact.

04

Before you ship

Use these as review criteria, not as a claim that the example above implements them.

  • Validate untrusted input against a versioned schema.
  • Bind evidence and approval to the exact draft revision.
  • Fail closed on missing sources and dependency errors.
  • Enforce release authorization on the server.
  • Test stale approvals, retries, and concurrent edits.
  • Record who released what, when, and from which sources.
The smallest useful test

Change one word in an approved draft. The next release attempt should require a new approval.

What this example intentionally leaves out

The types and helper functions are illustrative and are not implemented here. A production system also needs authentication, authorization, content sanitization, idempotent writes, audit retention, privacy controls, and evidence checking suited to the domain.

No model-generated text should execute as code or become trusted HTML. Treat retrieved material and generated content as untrusted input throughout the pipeline.
